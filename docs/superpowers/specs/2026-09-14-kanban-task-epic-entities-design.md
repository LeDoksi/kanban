# Канбан: задача и эпик как полноценные сущности

**Часть более крупного бэклога** («план №3») — фидбек владельца с первого
живого использования доски после плана №2 (`kanban` project, эпик `KAN-E5`
на самой доске). Бэклог разбит на независимые суб-проекты; это спека на
**суб-проект 1**. Остальные два («Навигация и структура проекта»,
«Вход и PWA») получат свои спеки отдельно, когда очередь дойдёт до них —
план не пытается закрыть их заодно.

**Родительская спека:** `docs/superpowers/specs/2026-09-11-kanban-design.md`
(модель данных, RLS, MCP-инструменты, технический стек — не повторяется
здесь, только то, что меняется или добавляется).

Не входит в эту спеку (сознательно, чинится отдельно без брейншторма —
обычные баги/полировка): перетаскивание между колонками (KAN-40),
откат карточки после drag (KAN-42), границы колонок (KAN-41), sticky
заголовок столбца (KAN-54), несходящиеся счётчики (KAN-53), техдолг
плана №2 (KAN-35..39).

## Цель

Сейчас с доски: нельзя редактировать или удалять задачу, эпик после
создания никуда не попадает и визуально нигде не виден, создание
задачи/эпика — две разные пугающие формы, комментарии только читаются, у
архива нет ни авто-, ни ручного управления. Цель — закрыть это одним
связным куском работы: задача и эпик становятся сущностями, с которыми
можно работать полностью из веба, без агента.

## `CreateModal.tsx` — единая модалка создания

Одна кнопка «Новая задача» в шапке (кнопка «Новый эпик» убирается).
Модалка открывается с переключателем наверху: **Задача** / **Эпик**
(два таба, как переключатель типа задачи в текущем `NewTask`).

- **Задача**: заголовок (переиспользует `guessType`/`stripPrefix` из
  `guess.ts`, как сейчас), тело (необязательно, `<textarea>`), тип
  (task/bug/chore — три кнопки, как сейчас в `NewTask`), чеклист
  (по строке на пункт), привязка к эпику — `<select>` со списком эпиков
  текущего проекта + «— без эпика —» (список эпиков: все, у кого есть
  хотя бы одна активная задача, плюс полностью пустые — то есть тот же
  «активный» набор, что и для заголовков на доске, см. `epics.ts` ниже;
  архивные эпики недоступны для выбора).
- **Эпик**: заголовок, цель (необязательно) — как в текущем `NewEpic`.

Логика создания (расчёт `seq`/`position`, вставка) переносится из
`NewTask.tsx`/`NewEpic.tsx` без изменений — меняется только форма и то,
что оба сценария живут в одном компоненте с общей подложкой/поведением
открытия-закрытия (Escape, клик по фону).

После создания задачи — закрыть модалку, доска обновится сама через
Realtime. После создания эпика — тоже просто закрыть модалку и остаться
на доске: сам эпик появится как заголовок в Backlog (см. ниже).

## `TaskModal.tsx` — расширения

- **Заголовок и тело — инлайн-редактирование.** Клик по тексту заголовка
  превращает его в `<input>`, клик по телу — в `<textarea>` (если тела
  не было — пустая textarea с плейсхолдером). Потеря фокуса или
  Enter/Ctrl+Enter сохраняет через `update({title})`/`update({body})` на
  Supabase напрямую. Отдельного «режима редактирования» нет.
- **Статус — кнопки, не `<select>`.** Те же 4 значения
  (`STATUS_LABEL`), кнопками в ряд, активная подсвечена. Логика записи
  (`status`+`closed_at`) не меняется, меняется только контрол.
- **Тип/лейбл — кнопки.** Те же три (task/bug/chore), тот же визуальный
  язык, что уже есть в `CreateModal`/бывшем `NewTask`. Пишет
  `update({type})`.
- **Привязка к эпику.** `<select>` с тем же списком «активных» эпиков,
  что и в `CreateModal`, плюс «— без эпика —». Меняет `epic_id`
  напрямую. Если у задачи сейчас стоит эпик, который стал архивным (все
  его задачи заархивированы, кроме этой) — он **обязан** остаться в
  списке как текущее выбранное значение, иначе можно случайно потерять
  информацию о привязке, просто открыв селект. Список = активные эпики
  ∪ {текущий `epic_id` задачи, если есть}.
- **Комментарии — можно писать.** Под существующим списком —
  `<textarea>` + кнопка «Отправить» (неактивна на пустом/пробельном
  тексте). Пишет `{item_id, author: 'me', body}` в `comments`, затем
  дозагружает список (или добавляет локально — решается при реализации,
  не архитектурный вопрос).
- **Архив.** Кнопка «В архив» — видна и активна только когда
  `status === 'done' && !archived_at`, пишет `archived_at: now()`.
  Кнопка «Вернуть в работу» — видна когда `archived_at` не пусто, пишет
  `status: 'doing', archived_at: null`.
- **Удаление.** Кнопка «Удалить» — подтверждение через нативный
  `confirm()` браузера (без отдельной модалки поверх модалки). Реальное
  удаление строки (`delete from items where id = ...`), не архивация.
  После успешного удаления — закрыть модалку и вызвать `onChanged`,
  чтобы доска перечиталась. Это единственное необратимое действие во
  всей спеке.
- Существующее (чеклист, ссылка «эпик: …» — заменяется кликабельным
  переходом в `EpicModal`, ошибки) остаётся как есть, с поправкой на то,
  что «эпик: …» теперь открывает `EpicModal`, а не `viewEpic`-экран.

## `EpicModal.tsx` — модалка эпика (замена `EpicScreen`)

Открывается кликом по заголовку эпика на доске или по ссылке «эпик: …»
в `TaskModal`. Содержимое = то, что уже показывает `EpicScreen` (цель,
прогресс `N/M`, ссылки на план/спеку, список задач, клик по задаче
открывает `TaskModal` поверх), плюс:

- Инлайн-редактирование заголовка и цели эпика — тот же клик-по-тексту
  паттерн, что в `TaskModal` (естественное расширение по аналогии, не
  было явно запрошено отдельно, но раз редактирование задачи уже
  инлайновое — для эпика тот же приём).
- Закрывается как обычная модалка (крестик/Escape/клик по фону), а не
  кнопкой «← Доска» — экрана эпика в отдельном URL/состоянии больше нет,
  `Board.tsx` теряет `viewEpic`/полноэкранный `if (viewEpic) return`.

## `epics.ts` — правила видимости эпика на доске

Единственный новый файл с логикой (не UI). Экспортирует чистые функции,
переиспользуемые и в `Board.tsx` (для заголовков), и в
`CreateModal`/`TaskModal` (для списка привязки) — чтобы не повторить
историю с KAN-35/36 (одна и та же логика, продублированная в двух
местах и разъехавшаяся).

Состояние эпика **не хранится** отдельным полем (`epics` не получает
`archived_at`) — вычисляется на лету из его задач:

- **Пустой** (ни одной задачи, `items.epic_id === epic.id` пусто во всём
  проекте) → активен, «домашняя» колонка — Backlog.
- **Есть хотя бы одна не архивная задача** → активен, заголовок
  появляется в каждой колонке, где у него реально есть не архивные
  задачи (и только там — если у него нет задач в Backlog, в Backlog он
  не показывается).
- **Есть задачи, но все архивные** → эпик сам архивный: не показывается
  нигде на доске (ни в одной колонке, ни в Backlog как пустой), не
  входит в список для привязки в `CreateModal`/`TaskModal` (кроме
  случая «это текущий `epic_id` редактируемой задачи», см. выше).

Само по себе это означает: если у заархивированного эпика оживает задача
(снята архивация — вручную кнопкой «Вернуть в работу», или новая задача
привязана к нему агентом через MCP), эпик на следующей перезагрузке сам
снова становится видимым — никакой отдельной операции «разархивировать
эпик» нет и не нужно.

**Компромисс, принятый явно:** раз архивный эпик не в списке для
привязки, вернуть к нему задачу через веб-интерфейс штатно нельзя —
только через агента (`update(id, {epic: "KAN-E7"})` уже это умеет, без
ограничений). Для личного инструмента с редким обращением к «мёртвым»
эпикам это приемлемо.

## Архивация задач: авто по времени + ручное управление

- **Авто.** Задача в статусе `done` дольше 3 дней автоматически
  архивируется. Реализация — `pg_cron` (расширение Postgres, доступно
  на бесплатном тарифе Supabase — проверить `list_extensions` на этапе
  реализации; если недоступно, откат на клиентскую проверку при заходе
  на сайт). Новая миграция:
  ```sql
  select cron.schedule(
    'archive-done-items',
    '0 3 * * *',
    $$ update items set archived_at = now()
       where status = 'done' and archived_at is null
         and closed_at < now() - interval '3 days' $$
  );
  ```
- **Ручной архив** — только из `status = 'done'` (кнопка в `TaskModal`,
  см. выше).
- **Ручной возврат** — переводит `status: 'doing'` (не `backlog`,
  не туда, где была раньше), снимает `archived_at` (кнопка в `TaskModal`
  и/или в `ArchiveList`).

Эта авто-архивация не меняет уже существующий видимый кап `DONE_SHOWN=5`
в колонке «Готово» — он остаётся display-time ограничением поверх
реально архивных (`archived_at`) карточек, как сейчас.

## Обработка ошибок

Тот же паттерн, что уже используется везде в проекте: локальный
`err`-стейт в компоненте, `setErr(error.message)` на любой неуспешный
Supabase-вызов, показ строкой в интерфейсе. Ничего нового не вводится.

Явные крайние случаи:
- Пустой комментарий — кнопка «Отправить» неактивна, запроса не будет.
- Удаление задачи — только после `confirm()`; сетевая ошибка удаления
  показывается как обычно через `err`, модалка не закрывается.
- Привязка к архивному эпику, который сейчас стоит у задачи — не
  выпадает из списка (см. правило выше), иначе можно молча стереть
  привязку, просто открыв `<select>`.

## Тестирование

Только `epics.ts` — чистые функции (группировка, «активен/пуст/архивен»
для одного эпика) — юнит-тесты в `web/test/epics.test.ts`, тот же
принцип, что у `position.test.ts`/`format.test.ts`. Всё остальное
(модалки, drag, кнопки, cron) — живая проверка на реальном сайте, без
моков — как договорено ещё в плане №2's Global Constraints.

## Глобальные ограничения (унаследованы из родительской спеки)

- Тарифы: только бесплатные (`pg_cron` — проверить доступность на
  бесплатном тарифе перед тем, как полагаться на него в плане).
- Доступ: RLS остаётся единственной проверкой прав, новых сущностей без
  политики не заводим (удаление и запись комментариев из веба уже
  укладываются в существующие политики `projects`/`items`/`comments` —
  владелец может всё, RLS проверяет email).
- Сервисный ключ Supabase никогда не попадает в репозиторий и в браузер
  (без изменений — этот суб-проект вообще не трогает MCP-сервер).
- Тесты — только на чистые функции (`epics.ts`). Компоненты
  веб-интерфейса — живьём, без моков.
- Язык: комментарии в коде, тексты интерфейса и сообщения коммитов — по-русски.
- Цвет несёт смысл. Новые элементы используют уже существующие токены
  — новых цветов не заводим.
- Удаление задачи — необратимое действие, единственное во всей спеке;
  подтверждается нативным `confirm()`, не отдельным UI.
