# Канбан: личная доска по проектам

**Дата:** 2026-09-11
**Статус:** спека согласована, реализация не начата

## Цель

Персональная система задач по нескольким проектам, в которой работают двое: владелец (человек) и Claude Code (агент). Человек заводит задачи с телефона и читает результат. Агент ведёт доску сам по ходу работы: раскладывает планы на карточки, отмечает прогресс, пишет краткие итоги, выносит наружу то, что требует ручного вмешательства.

Доска — общий планировщик и журнал работы одновременно. Не система отчётности перед начальством и не трекер времени.

## Ключевые ограничения

1. **Токен-экономика важнее полноты API.** Инструменты агента отдают сжатый текст, а не JSON. Инструментов мало (шесть), потому что их описания сидят в системном промпте каждого запроса.
2. **Читает агент по команде, пишет — всегда.** Автоматического опроса доски на старте сессии нет. Запись происходит без напоминаний, как часть работы над любым проектом.
3. **Телефон — основное место ввода.** Владелец добавляет задачи с телефона, а разбирает их за компьютером.
4. **Только один пользователь.** Вход по magic-link на `shakov.georgy@gmail.com`. Всё в бесплатных тарифах.
5. **Краткость отчётов — требование, а не пожелание.** Комментарий агента — одно-три предложения. Логи вызовов инструментов на доску не попадают никогда.

## Иерархия

```
Проект  (family-app)
  └─ Эпик   (E1 · Слой данных на Firestore)        ← один план superpowers
       └─ Задача (T-08 · Заметки на репозиторий)   ← один "### Task N"
            └─ Чеклист  ([ ] Step 1 … [ ] Step 6)
```

Задачи могут висеть прямо на проекте без эпика — так живут баги и техдолг, найденные вне планов.

## Модель данных

Postgres на Supabase. Четыре таблицы.

### `projects`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `text` PK | Человекочитаемый слаг: `family-app` |
| `name` | `text` | Отображаемое имя |
| `prefix` | `text` | Префикс ID задач: `FAM` |
| `repo_path` | `text` | Абсолютный путь к папке проекта |
| `position` | `double precision` | Порядок в списке |
| `archived_at` | `timestamptz` | NULL = активен |

`repo_path` — механизм определения контекста. MCP-сервер сравнивает текущую рабочую папку с этим полем и сам понимает, о каком проекте речь. Ни один инструмент не требует явно называть проект, пока работа идёт внутри его папки.

### `epics`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `text` PK | `FAM-E1` |
| `project_id` | `text` FK | |
| `title` | `text` | |
| `goal` | `text` | Секция Goal из плана |
| `plan_path` | `text` | Путь к `.md` плану |
| `spec_path` | `text` | Путь к `.md` спеке |
| `status` | `text` | `active` / `done` / `archived` |
| `position` | `double precision` | |
| `created_at` | `timestamptz` | |

### `items`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `text` PK | `FAM-12` |
| `seq` | `integer` | Номер внутри проекта, для генерации `id` |
| `project_id` | `text` FK | |
| `epic_id` | `text` FK NULL | NULL для задач вне планов |
| `type` | `text` | `task` / `bug` / `chore` |
| `title` | `text` | |
| `body` | `text` | Markdown: Files, Interfaces, подробности |
| `status` | `text` | `backlog` / `doing` / `waiting` / `done` |
| `checklist` | `jsonb` | `[{text, done}]` |
| `blocks` | `text[]` | ID задач, которые эта блокирует |
| `position` | `double precision` | Порядок внутри колонки |
| `created_by` | `text` | `me` / `claude` |
| `created_at`, `updated_at`, `closed_at` | `timestamptz` | |
| `archived_at` | `timestamptz` | Убирает из колонки «Готово», но не удаляет |

`status` = колонка на доске. Полей «исполнитель» и «приоритет» нет намеренно: `waiting` уже отвечает на вопрос, чья очередь.

### `comments`

| Поле | Тип | Смысл |
|---|---|---|
| `id` | `bigserial` PK | |
| `item_id` | `text` FK | |
| `author` | `text` | `me` / `claude` |
| `body` | `text` | |
| `created_at` | `timestamptz` | |

### Решения, принятые из-за стоимости изменения

**ID вида `FAM-12`.** Читаемы человеком вслух, дёшевы в токенах. UUID стоил бы примерно 15 лишних токенов на каждое упоминание задачи.

ID **не кодирует тип задачи**: префикс всегда принадлежит проекту. Иначе переквалификация задачи в баг меняла бы её идентификатор, и все ссылки на неё — в коммитах, комментариях, `blocks` — протухали бы. Тип живёт в своём поле и показывается значком.

Эпики нумеруются отдельным счётчиком того же проекта: `FAM-E1`, `FAM-E2`.

Генерация: `seq = (select coalesce(max(seq),0)+1 from items where project_id = $1)` внутри транзакции.

`ponytail: гонка при одновременной записи из двух сессий даст конфликт по PK; писателей двое, повтор транзакции решает. Перейти на sequence-на-проект, если станет мешать.`

**`position` — дробное число.** Вставка между соседями = среднее, переписывается одна строка.

`ponytail: после примерно 50 вставок в одну и ту же точку упирается в точность double. Перенумеровать колонку целыми при обнаружении разрыва меньше 1e-9.`

**`checklist` — структура, а не markdown.** Позволяет рисовать «3/6» и отмечать шаг точечно, не переписывая тело задачи.

**`archived_at` с первого дня.** Колонка «Готово» иначе становится нечитаемой за несколько месяцев.

### Доступ

RLS на всех таблицах, политика сверяет email из JWT с адресом владельца (`shakov.georgy@gmail.com`) и разрешает все операции только ему.

Веб-клиент ходит с anon-ключом под magic-link сессией и упирается в эту политику. MCP-сервер ходит с ключом `service_role`, который лежит только в локальном конфиге на машине владельца и в браузер не попадает никогда.

## Инструменты агента (MCP)

Шесть инструментов. Проект по умолчанию определяется по рабочей папке через `projects.repo_path`.

### `board(project?, epic?)`

Сводка доски. Формат ответа:

```
family-app · E1 Firestore (7/15)
 8 ▸ Заметки на репозиторий            doing    3/6
 9   Списки и хотелки                  backlog
12 ! Включить Firestore в консоли      waiting
14 · Календарь не листает в ноябрь     bug      backlog
```

Внутри одного проекта префикс не печатается — шапка уже сказала, какой это проект. Полная форма `FAM-14` появляется только когда речь идёт о нескольких проектах сразу. Тип печатается словом лишь тогда, когда он не `task`.

Закрытые задачи не показываются — только счётчик в шапке. Целевой размер ответа: до 300 токенов на проект.

### `get(id)`

Полное тело задачи, чеклист и комментарии. Вызывается только для той задачи, которую агент реально берёт в работу.

### `add(items[])`

Создание. Принимает **массив** — пятнадцать задач одного плана заводятся одним вызовом, а не пятнадцатью.

Ответ: `FAM-23..FAM-37 создано` — без эха объектов.

### `update(id, {status?, title?, body?, check?, uncheck?, epic?, archive?})`

`check` и `uncheck` принимают индекс шага или его текст.

Ответ: одна строка подтверждения.

### `comment(id, text)`

Запись в журнал задачи.

### `import_plan(path, project?)`

Разбирает файл плана superpowers и заводит эпик со всеми задачами одним вызовом.

Правила разбора:

| Элемент плана | Становится |
|---|---|
| `# План №N: <title>` | Эпик |
| `**Goal:**` | `epics.goal` |
| `**Spec:**` ссылка | `epics.spec_path` |
| `### Task N: <title>` | Задача |
| `**Files:**`, `**Interfaces:**` | `items.body` |
| `- [ ] **Step N: <text>**` | Элемент чеклиста |

Шаг, помеченный как ручной (содержит «ручной шаг», «выполняет владелец», «в консоли»), выносится **отдельной задачей** со статусом `waiting` и связывается через `blocks` с задачей, из которой он изъят.

`ponytail: распознавание ручных шагов — эвристика по ключевым словам. Агент обязан проверить результат импорта глазами и поправить, а не полагаться на парсер.`

Парсер — самая рискованная часть системы и единственная, которая разрабатывается строго через TDD: тесты пишутся на реальном файле `2026-09-09-firestore-data-layer.md` (15 задач, 93 шага, из них один ручной — в Task 1).

Разметку внутри блоков ``` парсер обязан игнорировать. План про инструменты вполне может содержать пример другого плана целиком, и заголовки внутри примера структурой не являются.

## Интерфейс

### Общие принципы

- Цвет несёт смысл и только его: янтарный — «ждёт тебя», красный — баг, зелёный — закрыто. Всё остальное серое.
- У карточек нет рамок, только фон. Разделители — между колонками.
- Заголовки и подписи в предложении, не Title Case.
- Тёмная тема обязательна.

### Десктоп — доска

Четыре колонки: **Backlog → В работе → Нужно от тебя → Готово**. Перетаскивание мышью. Шапка показывает `проект / эпик` и прогресс; клик по имени проекта открывает переключатель.

«Готово» показывает последние несколько карточек и схлопывается в ссылку на архив.

### Десктоп — экран эпика

Плоский список задач строками, а не колонками. Раскрыта только задача в работе: её чеклист и комментарии агента видны сразу, остальные свёрнуты в строку. В шапке — цель, прогресс и ссылки на `.md` план и спеку.

### Телефон — список

Не доска. Одна вертикаль, сгруппированная по статусу, в порядке: «Нужно от тебя» → «В работе» → Backlog. Свайп по карточке меняет статус. Кнопка «+» в правом нижнем углу.

Заведение задачи — одно текстовое поле. Тип определяется по тексту («баг:», «починить»), проект берётся последний открытый; и то и другое правится одним тапом по пилюле.

### Живое обновление

Supabase Realtime: пока агент работает и пишет через MCP, открытая доска обновляется сама. Отдельной кнопки «обновить» нет.

### Экран «Все проекты»

По строке на проект: сколько задач ждёт владельца, чем занят агент, прогресс активного эпика. Строится **после** основной доски — при четырёх проектах пока не нужен.

## Правила работы агента

Записываются в `~/.claude/CLAUDE.md`, один раз на все проекты.

Работа над проектом идёт тремя способами, и доска ведётся во всех трёх: по плану, без плана (владелец попросил что-то сделать прямо сейчас) и по ходу (владелец вмешался в идущую работу). Привязка триггеров к наличию плана была бы ошибкой — без плана делается не меньше работы, чем по плану.

| Событие | Действие |
|---|---|
| Написан план через `writing-plans` | `import_plan` немедленно |
| **Владелец попросил сделать что-то без плана** | **карточка заводится до начала работы**, сразу `doing` |
| **Владелец добавил требование в идущую работу** | новая карточка в тот же эпик — или пункт чеклиста, если это шаг внутри текущей задачи |
| **Проект добивается без плана** | каждая осмысленная единица — отдельная карточка, эпика может не быть |
| Задача взята в работу | `status` → `doing` |
| Упёрся в ручной шаг или вопрос | карточка в `waiting`, **работа останавливается** |
| Найден баг или долг мимо текущей темы | карточка в `backlog`, работа продолжается |
| Задача закончена | `comment` с итогом + `status` → `done` |

**Порог заведения карточки.** Карточка заводится, если работа оставляет след: правку в файле, коммит, решение, находку. Не заводится на чтение, поиск, ответ на вопрос и разовую однострочную правку по ходу разговора. Сомнение трактуется в пользу заведения — лишнюю карточку владелец закроет за секунду, пропущенная работа исчезает из истории навсегда.

**Карточка заводится до работы, а не после.** Тогда владелец, открыв доску с телефона, видит, чем агент занят прямо сейчас, а не узнаёт об этом задним числом.

**Формат комментария — жёстко.** Одно-три предложения: что сделано, что обнаружено по пути, что с этим сделано. Логи вызовов инструментов, перечисление прочитанных файлов и промежуточные попытки на доску не попадают.

**Доска и `.md` план не спорят.** Файл плана остаётся тем, по чему идёт исполнение; доска — тем, где видно состояние. Синхронизация на границах задач, не на каждом шаге.

Правило в `CLAUDE.md` не является гарантией соблюдения. Если доска начнёт отставать от реальности, добавляется хук на завершение сессии, который это проверяет. Заранее он не строится.

## Технический стек

| Слой | Выбор |
|---|---|
| База и auth | Supabase (Postgres, magic-link, RLS, Realtime) |
| Веб-клиент | React + Vite + TypeScript + Tailwind |
| Перетаскивание | `@dnd-kit/core` |
| Хостинг клиента | GitHub Pages, статика через GitHub Actions |
| MCP-сервер | Node + TypeScript, `@modelcontextprotocol/sdk`, транспорт stdio |

MCP-сервер запускается локально на машине владельца и ходит в Supabase напрямую с ключом `service_role`. Промежуточного API-слоя нет: он добавил бы деплой, латентность и точку отказа, ничего не дав единственному пользователю.

## Что сознательно не строится

Метки, спринты, оценки времени, диаграммы сгорания, вложения, несколько досок на проект, треды в комментариях, уведомления, мобильное приложение, поле «исполнитель», приоритеты.

Всё перечисленное добавляется одной миграцией и одним экраном, когда в нём появится нужда. Ни одно из них не влияет на решения, принятые выше.

## Порядок сборки

Спека разбивается на два плана. Граница проведена так, чтобы первый план закончился **работающей системой для обоих**, а не половиной, которой никто не может пользоваться.

### План №1 — рабочий минимум

1. Схема Supabase, RLS, вход по magic-link.
2. MCP-сервер: шесть инструментов, сжатые форматы ответов.
3. Парсер планов через TDD на файле `2026-09-09-firestore-data-layer.md`.
4. Веб-клиент: доска на четыре колонки и заведение задачи. Без перетаскивания — статус меняется выбором.
5. Правила в `~/.claude/CLAUDE.md`.
6. Живая проверка: импорт реального плана, работа по нему один вечер.

После этого плана агент ведёт доску, а владелец её читает и пополняет. Всё остальное — удобство.

### План №2 — удобство

Экран эпика, мобильный список со свайпом, перетаскивание мышью, архив, Realtime, экран «Все проекты».

Упаковка MCP-сервера в `.mcpb` (Desktop Extension) — установка через Settings → Extensions вместо `claude mcp add` в терминале. Не раньше, чем сервер стабилизируется: пока код меняется каждый день, пересобирать `.mcpb` при каждой правке дороже, чем один раз переуказать путь в CLI-команде.

Второй план пишется **после того, как первый прожил несколько дней**. За это время станет видно, что из списка выше на самом деле нужно, а что было придумано заранее.
